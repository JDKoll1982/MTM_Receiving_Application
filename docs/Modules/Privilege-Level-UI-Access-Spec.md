# Privilege Level UI Access Spec

Last Updated: 2026-03-23
Status: Draft for approval
Scope: Cross-module privilege visibility and enforcement, with immediate focus on `View_Settings_Users.xaml` privilege editing.

## Goal

Define:

- which UI surfaces and actions should be visible or enabled for `User`, `Supervisor`, `Admin`, and `Developer`
- what must change in `View_Settings_Users.xaml` so an authorized operator can edit the selected user's effective privilege level
- which files, methods, variables, MySQL tables, and stored procedures are impacted across all modules
- which assumptions need user confirmation before implementation starts

## Existing Guards That Are Not Privilege Guards

The following confirmed guard classes are important because they may look like access control during review, but they are not actually role/privilege enforcement:

| Guard Category             | Examples                                                              | Why It Does Not Solve Privilege Access                                             |
| -------------------------- | --------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Selection guards           | `HasSelectedUser`, `IsPartSelected`, `CanEdit()` on selected shipment | Only checks that a row or record is selected                                       |
| Busy guards                | `if (IsBusy) return;`, `!IsBusy` in `CanExecute`                      | Only prevents concurrent execution                                                 |
| Validation guards          | quantity > 0, required field checks, package type required            | Only enforces valid data entry                                                     |
| Workflow state visibility  | `IsModeSelectionVisible`, `IsEditModeVisible`, etc.                   | Only decides which workflow step is active                                         |
| Settings permission checks | `SetSettingCommandHandler.HasPermissionAsync()`                       | Protects settings writes, not general feature navigation or privileged UI surfaces |

## Fourth-Pass Enhancement Notes

This document has now been through four passes:

- Pass 1: broad cross-module inventory and initial privilege matrix
- Pass 2: settings-shell navigation review plus existing command-guard review
- Pass 3: top-level main-shell exposure, unconditional DI registration review, and risk correction for Ship/Rec `Clear`
- Pass 4: settings host behavior, page code-behind command paths, service-locator constraints, and authorization-plumbing reality check

The main conclusion from the fourth pass is that the privilege model needs to be resilient to more than just routed navigation. In this codebase, privileged pages and commands can also be reached through:

1. host services such as `Service_SettingsWindowHost`
2. page code-behind click handlers
3. direct service-location via `App.GetService<T>()`

That means the eventual implementation should treat navigation filtering as necessary but insufficient. The real enforcement boundary has to live in shared authorization checks used by shells, host services, ViewModels, and sensitive command handlers.

## Third-Pass Enhancement Notes

This document has now been through three passes:

- Pass 1: broad cross-module inventory and initial privilege matrix
- Pass 2: shell/navigation review inside Settings plus existing command-guard review
- Pass 3: top-level main-shell exposure, unconditional DI registration review, and correction of overstated risk on Ship/Rec `Clear`

The main conclusion from the third pass is that the privilege model needs three enforcement layers, not one:

1. root shell navigation filtering
2. settings/module page navigation filtering
3. command/service-level authorization for privileged actions

It also confirms that DI registration should remain unconditional unless you explicitly want a more radical architecture shift. The lower-risk path is to add a shared authorization service and apply it at navigation and command boundaries.

## Second-Pass Enhancement Notes

This document has now been through two passes:

- Pass 1: broad cross-module inventory and initial privilege matrix
- Pass 2: shell/navigation review plus existing command-guard review, intentionally avoiding deep rescans of the same primary methods

The main conclusion from the second pass is that the codebase already has strong patterns for:

- `IsBusy` guards
- row-selection guards
- validation guards
- workflow-step visibility guards

What it does not have yet is a shared, explicit privilege-access layer that plugs into those same patterns. That should keep the eventual implementation focused and smaller than a full UI redesign, provided the assumptions in this document are approved.
