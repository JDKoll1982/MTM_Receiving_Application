Chapter 06

Database and SQL

Review, optimisation, and DBA tooling for the two database systems this application touches: MySQL 5.7 (read/write) and the Infor Visual MTMFG SQL Server (strictly read-only). Every prompt below assumes this repo's database discipline: MySQL writes go through stored procedures only, and nothing ever writes to Infor Visual.

The rules those tools must enforce live in .github/instructions/database/; the schema reference CSVs live in docs/development/InforVisual/DatabaseCSVFiles/, and the SQL source of truth lives under Database/.

sql-code-review

database-data-management@1.0.0

Universal SQL code review covering SQL injection, access control, naming standards, and anti-patterns across MySQL, SQL Server, and other dialects.

  • Reviewing a new stored procedure under Database/Database_Deployment/Sql_Files/StoredProcedures/ before it ships to MySQL 5.7.
  • Checking that an Infor Visual query in Database/InforVisualScripts/Queries/ stays read-only and parameterized.
  • Auditing a DAO change in Module_Receiving/Data/ for injection-safe calls and correct Model_Dao_Result handling.
Prerequisites
The SQL text or the diff to review. It reads files and flags problems rather than guessing at the schema.
Boundaries
Reviews only. It does not write schema or stored procedures, and it cannot reproduce MySQL-version behaviour that only mtm_receiving_application_test reveals.
Review every file under Database/Database_Deployment/Sql_Files/StoredProcedures/Receiving/
for SQL injection, missing parameterization, and naming that deviates from the
sp_Receiving_* convention. Flag anything that writes to the Infor Visual MTMFG
database, and anything that performs a MySQL write outside a stored procedure.

sql-optimization

database-data-management@1.0.0

Query tuning, indexing strategy, execution-plan reading, and pagination guidance for slow or large SQL.

  • Tuning a slow MySQL stored procedure against mtm_receiving_application_test before touching production.
  • Reading the plan of a reporting query under Database/Database_Deployment/Sql_Files/CustomPrompts/ to find missing indexes.
  • Adding pagination to an unbounded result set instead of loading it whole into an ObservableCollection.
Prerequisites
The query or stored procedure text, ideally with an EXPLAIN output or execution plan to ground the advice.
Boundaries
Advises on SQL; it does not edit schema or create indexes itself. Any schema or stored-procedure change still needs approval under this repo's rules.
Optimize the stored procedures in
Database/Database_Deployment/Sql_Files/StoredProcedures/Reporting/. For each one,
identify missing indexes, suggest an EXPLAIN-based check against
mtm_receiving_application_test, and add pagination where the result set is unbounded.
Do not propose schema or stored-procedure changes without flagging them for approval.

postgresql-code-review

database-data-management@1.0.0

PostgreSQL-specific code review covering JSONB, arrays, custom types, row-level security, and PostgreSQL-only anti-patterns.

  • Reviewing PostgreSQL DDL if a PostgreSQL target is ever added alongside MySQL 5.7 and Infor Visual SQL Server.
  • Evaluating jsonb and array usage in a PostgreSQL migration script for type and indexing mistakes.
  • Checking that row-level security is enabled on a multi-tenant PostgreSQL schema.
Prerequisites
PostgreSQL SQL to review. There is none in this repo today, so this only becomes relevant if a PostgreSQL target appears.
Boundaries
PostgreSQL only. This repo uses MySQL 5.7 (read/write) and Infor Visual SQL Server (read-only), so it does not understand MySQL or T-SQL conventions and should not be applied to them.
Only if a PostgreSQL target is added to this repository, review its DDL and
queries for jsonb misuse, array pitfalls, and missing row-level security. Today this
repo is MySQL 5.7 plus read-only Infor Visual SQL Server, so confirm a PostgreSQL
target actually exists before applying this review.

postgresql-optimization

database-data-management@1.0.0

PostgreSQL-specific performance work: indexing, query planning, partitioning, and PostgreSQL-only tuning features.

  • Tuning a slow PostgreSQL query with EXPLAIN ANALYZE if PostgreSQL is introduced as a target database.
  • Advising on partial, expression, or GIN indexes for a PostgreSQL schema.
  • Recommending partitioning or connection-pooling settings for a PostgreSQL workload.
Prerequisites
PostgreSQL SQL and, where possible, an EXPLAIN ANALYZE plan to optimise against.
Boundaries
PostgreSQL only. This repo uses MySQL 5.7 and Infor Visual SQL Server, so apply it only when a PostgreSQL target actually appears.
Only if a PostgreSQL target is added to this repository, optimize its queries:
read EXPLAIN ANALYZE plans, propose indexes, and recommend partitioning where tables
are large. Today this repo is MySQL 5.7 plus read-only Infor Visual SQL Server, so
confirm a PostgreSQL target exists before applying PostgreSQL-only tuning.

ms-sql-dba

database-data-management@1.0.0

Microsoft SQL Server DBA agent for T-SQL queries, administration, and investigation against the Infor Visual MTMFG database.

  • Authoring a new read-only SELECT against MTMFG, verifying column names against docs/development/InforVisual/DatabaseCSVFiles/ first.
  • Running and refining a query saved under Database/InforVisualScripts/Queries/ against the read-only connection.
  • Diagnosing a slow query on large tables such as RECEIVER_LINE or INVENTORY_TRANS.
Prerequisites
A SQL Server connection whose string carries ApplicationIntent=ReadOnly, plus the CSV schema reference for column verification.
Boundaries
SQL Server only. It must never INSERT, UPDATE, or DELETE against Infor Visual, which is strictly read-only in this repo, and it does not manage MySQL.
Use the ms-sql-dba agent to write a new SELECT against MTMFG (Infor Visual).
Verify column names against docs/development/InforVisual/DatabaseCSVFiles/ before
writing the query, keep ApplicationIntent=ReadOnly in the connection string, and save
the finished query under Database/InforVisualScripts/Queries/. No INSERT, UPDATE, or
DELETE.

postgresql-dba

database-data-management@1.0.0

PostgreSQL DBA agent for administration, schema design, and query work against a PostgreSQL database.

  • Standing up and administering PostgreSQL only if it is added as a target database for this application.
  • Designing a PostgreSQL schema, roles, and grants for a future data store.
  • Investigating PostgreSQL locks, vacuum, or replication issues in that future target.
Prerequisites
A PostgreSQL target to administer. None exists in this repo today, so this agent is dormant until one appears.
Boundaries
PostgreSQL only. It does not apply to MySQL 5.7 or Infor Visual SQL Server, which are the two databases this repo actually uses.
Only if a PostgreSQL target is added to this repository, use the postgresql-dba
agent to design its schema, roles, and grants and to administer it. Today this repo is
MySQL 5.7 plus read-only Infor Visual SQL Server, so confirm a PostgreSQL target
exists before using this agent.

The database discipline comes first. MySQL 5.7 is read/write, but every write must go through a stored procedure under Database/Database_Deployment/Sql_Files/StoredProcedures/; raw MySQL SQL in C# is forbidden, and DAOs in Module_*/Data/ return Model_Dao_Result / Model_Dao_Result<T> instead of throwing. Infor Visual (MTMFG) is strictly read-only: no INSERT, UPDATE, or DELETE, and the connection string must carry ApplicationIntent=ReadOnly. Reach for sql-code-review before merging any SQL, sql-optimization when a query is slow, and ms-sql-dba for new Infor Visual SELECTs. The PostgreSQL tools are dormant here; use them only if a PostgreSQL target ever appears.
