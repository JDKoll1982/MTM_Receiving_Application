Chapter 01

Spec-driven development

Planning work before code exists. Spec Kit and its extensions take a feature from an idea through assessment, specification, planning, task breakdown, implementation, and convergence, with a live companion canvas and per-step bookkeeping state.

Everything here writes under specs/ and .specify/. The code they plan and build is the same WinUI 3, .NET 10, MVVM View→ViewModel→Service→DAO stack that the rest of this book documents, so a spec's implementation tasks still obey the house rules: MySQL 5.7 writes go through stored procedures, Infor Visual SQL Server stays read-only, and tests are xUnit with FluentAssertions.

speckit-companion

speckit-companion@0.2.1

Renders a live board of every spec in flight: the specify→plan→tasks→implement pipeline, task progress, run history, and a next-step button that advances the active feature.

  • Watching the active specs/ feature move through plan, tasks, and implement without re-reading the .md files by hand.
  • Seeing at a glance which tasks in tasks.md are done, in progress, or still pending while implementing a Module_Receiving change.
  • Resuming a half-finished feature by clicking the next-step button instead of remembering which command comes next.
How to open
Ask for the companion board in chat; the canvas opens beside the conversation and reads its state from the .spec-context.json that the companion agents write.
Boundaries
It displays and steps through specs; it does not author them. The pipeline agents below do the actual work.

speckit.specify

.github/agents/speckit.specify.agent.md

Creates or updates a feature specification from a natural-language description, writing spec.md into a numbered specs/NNN-slug/ directory and validating it against a quality checklist.

  • Starting a new feature by describing it in one sentence and getting a spec.md with user scenarios, functional requirements, and success criteria.
  • Fixing an existing spec in place when requirements drift, rather than rewriting the feature from scratch.
  • Recording the feature directory in .specify/feature.json so speckit.plan and speckit.tasks can find it without guessing.
Prerequisites
A feature description in the message. Everything else is created by the agent.
Boundaries
Writes the spec and checklist only. It never touches application code or the MVVM layers.
/speckit.specify Add a two-tab analytics screen to Module_Reporting: one tab for
receipt counts by vendor, one for line discrepancies against Infor Visual. Keep it read-only.

speckit.plan

.github/agents/speckit.plan.agent.md

Executes the planning workflow from the spec, producing an implementation plan with research and design artifacts.

  • Turning an approved spec.md into a plan.md that names the ViewModel, Service, and DAO files a feature will touch.
  • Deciding up front whether a feature needs a new MySQL stored procedure or only a read-only Infor Visual query, before any code is written.
  • Recording architecture and data-model choices so speckit.tasks can break the plan into ordered, buildable tasks.
Prerequisites
A completed spec.md in the feature directory.
Boundaries
Designs; it does not write production code or break the plan into tasks.
/speckit.plan Plan the two-tab Module_Reporting analytics feature. Keep every MySQL
write behind a stored procedure and treat the Infor Visual connection as read-only, following
the DAO pattern in Module_Reporting/Data/.

speckit.tasks

.github/agents/speckit.tasks.agent.md

Generates an actionable, dependency-ordered tasks.md for the feature from the spec and plan artifacts.

  • Producing a phase-by-phase task list that orders the DAO before the Service and the Service before the ViewModel, matching the MVVM dependency direction.
  • Tagging tasks that touch MySQL stored procedures so they are implemented and tested as a group.
  • Handing a complete task list to speckit.implement so it can execute the feature in dependency order.
Prerequisites
A spec.md and a plan.md in the same feature directory.
Boundaries
Breaks work down; it does not perform any of the tasks itself.
/speckit.tasks Generate tasks for the analytics feature. Order the DAO work before the
Service work, keep FluentAssertions tests on the plan, and name any test data with a TEST-
prefix.

speckit.implement

.github/agents/speckit.implement.agent.md

Executes the implementation plan by processing every task in tasks.md in dependency order until the feature is built.

  • Building a feature end to end, task by task, so each ViewModel, Service, and DAO lands in the right layer.
  • Running the narrowest build or test slice after each task instead of waiting for a full solution run.
  • Stopping at the first failing task and reporting it, rather than silently continuing past a broken build.
Prerequisites
A complete, ordered tasks.md produced by speckit.tasks.
Boundaries
Implements what the tasks say; it does not redesign the plan or add scope of its own.
/speckit.implement Implement the tasks for specs/003-agent-toolkit-book/tasks.md. After each
task, run the narrowest dotnet build or dotnet test slice that can fail the change, and stop on
the first failure.

speckit.converge

.github/agents/speckit.converge.agent.md

Assesses the codebase against the spec, plan, and tasks, then appends any remaining unbuilt work as a new Convergence phase in tasks.md.

  • Catching requirements in spec.md that speckit.implement missed or only partially built, and re-queuing them as tasks.
  • Verifying that each task's promised files actually exist and satisfy the acceptance criteria, rather than trusting a green checkmark.
  • Leaving tasks.md byte-for-byte unchanged when the code already meets every requirement, so the feature can be declared done.
Prerequisites
spec.md, plan.md, and a tasks.md that speckit.implement has already run.
Boundaries
Append-only: it writes new tasks but never edits existing ones, the spec, the plan, or any application code.
/speckit.converge Converge the analytics feature. Treat the constitution in
.specify/memory/constitution.md as non-negotiable, and append any missing or partial work as a
new phase without rewriting existing tasks.

speckit.analyze

.github/agents/speckit.analyze.agent.md

Performs a non-destructive cross-artifact consistency and quality analysis across spec.md, plan.md, and tasks.md after task generation.

  • Finding a task in tasks.md that has no matching requirement in spec.md, or a requirement with no task at all.
  • Confirming the plan's file references match the real MVVM layout, so a task cannot point at a ViewModel that does not exist.
  • Running a read-only consistency pass before implementation so gaps are caught while they are cheap to fix.
Prerequisites
All three artifacts present in one feature directory.
Boundaries
Read-only. It reports inconsistencies but changes no files.
/speckit.analyze Analyze specs/003-agent-toolkit-book/ for consistency between spec.md,
plan.md, and tasks.md. Report gaps and contradictions only; do not modify the files.

Reports living-spec requirement to test coverage: per requirement, whether its coverage tier maps an xUnit test, read-only.

  • Checking which living-spec requirements have a matching xUnit test and which do not.
  • Spotting a DAO behavior that is specified but untested before a refactor.
Boundaries
Not invoked as a verb; it reports coverage and never halts or writes files.

speckit.companion.living-drift

.github/agents/speckit.companion.living-drift.agent.md

Reports living-spec drift: per capability, the source files changed since the spec was last committed, read-only.

  • Finding a ViewModel or Service file that changed after its living spec was last committed.
  • Deciding whether a spec needs a sync pass before a code review.
Boundaries
Not invoked as a verb; it reports drift and never halts or writes files.

speckit.companion.living-move

.github/agents/speckit.companion.living-move.agent.md

Moves a living spec between central and colocated storage, file, tiers, and registry together, reversible.

  • Relocating a colocated Module_Dunnage spec to the central specs folder when it grows beyond one module.
  • Moving a central spec beside its owning module for a tighter edit loop.
Boundaries
Not invoked as a verb; it moves specs and their registry entries, not code.

speckit.companion.living-show

.github/agents/speckit.companion.living-show.agent.md

Prints one slice of a living spec: a capability's requirement headings, one requirement in full, or the requirements that describe one file.

  • Reading just the requirements that describe Dao_ReceivingLine without opening the whole spec.
  • Showing one capability's headings to check scope before editing.
Boundaries
Not invoked as a verb; it prints slices, read-only, never halts or writes.

speckit.companion.living-sync

.github/agents/speckit.companion.living-sync.agent.md

Syncs living specs from your current changes: groups working-tree changes, uncommitted included, by capability and updates every affected spec in one pass.

  • Updating the Module_Receiving living spec after editing its DAO and Service so the spec matches the working tree.
  • Folding uncommitted changes into the spec in one pass before a commit.
Boundaries
Not invoked as a verb; it updates specs in place and never regenerates them.

speckit.companion.living-validate

.github/agents/speckit.companion.living-validate.agent.md

Checks the shape of living specs and a feature spec's deltas: a requirement with no scenario, a scenario missing WHEN or THEN, a duplicate heading, or a delta pointing at nothing.

  • Validating that every living-spec requirement has a scenario with WHEN and THEN before relying on the spec.
  • Catching a duplicate heading or a delta that references a deleted file.
Boundaries
Not invoked as a verb; it validates shape, read-only, never halts or writes.

Choosing between them. Run the pipeline agents in order, specify, plan, tasks, implement, converge, and reach for the companion verbs when you want the board to track the same steps. Use the assessment and bug extensions before the pipeline, for ideas and defects that are not yet ready to become specs. The companion bookkeeping and living-spec agents are not run by hand; they keep state and living specs in sync around the verbs.
