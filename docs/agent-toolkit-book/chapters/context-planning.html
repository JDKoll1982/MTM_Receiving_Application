Chapter 10

Context, planning, and testability

Planning a change before touching code, and making that code testable once you do. The context-engineering plugin maps files and sequences refactors; the dotnet-test plugin finds what has no tests and adds the seams — TimeProvider, file wrappers, deterministic clocks — that let the 300+ C# files across fifteen Module_* projects be tested without wall clocks and real I/O.

This chapter covers planning and seams, not the act of writing or running tests. Test generation, execution, coverage collection, and quality analysis live in their own chapter.

context-map

context-engineering@1.0.0

Generates a map of every file relevant to a task — files to modify, dependencies, tests, and reference patterns — before any code is changed.

  • Mapping a Module_Receiving change so the View, ViewModel, Service, DAO, and their tests appear in one table before you touch anything.
  • Confirming a cross-module change does not break the View → ViewModel → Service → DAO layering or leak a Dao_* reference into a ViewModel.
  • Surfacing the MySQL stored-procedure file under Database/ that a DAO change will depend on, before you edit the C#.
Prerequisites
A concrete task description. The skill maps; it does not implement.
Boundaries
Produces a reviewable map and stops. It does not edit files and does not use Serena's symbol index — pair it with Serena for symbol-level precision on the 300+ C# files.
Use the context-map skill for: add a GetByLoadAsync method to the
Module_Receiving receiving-line DAO. Map the files to modify, their
dependencies, the tests under MTM_Receiving_Application.Tests/, and a
reference pattern from an existing DAO in the module. Include risk items for
the MVVM layering and the MySQL stored-procedure boundary.

refactor-plan

context-engineering@1.0.0

Produces a phased, sequenced plan — types first, then implementations, callers, tests, cleanup, with verification and rollback steps — and waits for confirmation before editing.

  • Sequencing a rename across Module_Receiving so interfaces change before implementations before callers before tests.
  • Planning a move of shared code into Module_Shared without breaking the View → ViewModel → Service → DAO rule.
  • Gating any refactor of DAO methods that must keep returning Model_Dao_Result rather than throwing.
Prerequisites
Enough codebase knowledge to identify affected files; the skill investigates first.
Boundaries
Plans and stops for confirmation — it makes no edits. Serena is the symbol-level tool for finding every caller of a signature you plan to change.
Use the refactor-plan skill to plan renaming CurrentLineID to CurrentLoadID
in Module_Receiving. Investigate callers with Serena's find_referencing_symbols
first, then output the plan with phases, verification (dotnet build
MTM_Receiving_Application.slnx), and rollback. Wait for my confirmation before
editing.

find-untested-sources

Pairs source files to their tests and lists source files or modules that have no corresponding test, using Roslyn for C#.

detect-static-dependencies

dotnet-test@1.0.0

Locates hard-to-test ambient C# calls — DateTime.Now, File, Directory, Environment, HttpClient, Console, Process — across the codebase.

  • Finding every DateTime.Now in Module_Receiving services that would make a test time-dependent.
  • Checking whether a DAO's file access or a service's Environment call blocks deterministic tests.
  • Verifying a class is already abstracted behind TimeProvider before you add a wrapper.
Prerequisites
The target must explicitly be C#/.NET work, or the skill stays dormant.
Boundaries
Only locates the statics; it does not add seams — use generate-testability-wrappers next.
Use the detect-static-dependencies skill on Module_Reporting. Find every
System.DateTime.Now/UtcNow, File, Directory, and Environment call in the
module's services and DAOs, and report which are already behind an injected
abstraction.

generate-testability-wrappers

dotnet-test@1.0.0

Adds the smallest injectable seam — a TimeProvider, IFileSystem, or Environment/Console/Process wrapper — when C# code calls an ambient static and no seam exists.

  • Introducing TimeProvider into a receiving service that stamps received timestamps so tests can freeze time.
  • Wrapping File reads in Module_Settings.Core so a settings load can be tested without touching disk.
  • Registering the new seam in Infrastructure/DependencyInjection so the app still resolves it.
Prerequisites
A static call with no existing injected interface or built-in abstraction.
Boundaries
Does not migrate callers that already consume an abstraction — that is migrate-static-to-wrapper.
Use the generate-testability-wrappers skill to introduce TimeProvider into
the receiving-line service that stamps receive timestamps. Keep the MVVM
boundary intact, register the seam in Infrastructure/DependencyInjection, and
confirm the DAO still returns Model_Dao_Result.

dotnet-test@1.0.0

Replaces existing C# static calls with a named wrapper or built-in abstraction across scoped files, including constructor injection and DI wiring.

  • Migrating DateTime.UtcNow to TimeProvider across Module_Receiving services while preserving DateTimeKind.
  • Swapping File.* calls to IFileSystem in Module_Settings.Core's settings loader.
  • Wiring the migration through Infrastructure/DependencyInjection without touching App.xaml.cs directly.
Prerequisites
A chosen seam or built-in abstraction, and the scoped files to migrate.
Boundaries
Migrates to an existing abstraction; it does not design a new wrapper — use generate-testability-wrappers for that.
Use the migrate-static-to-wrapper skill to migrate DateTime.UtcNow to
TimeProvider in Module_Receiving/Data/Dao_ReceivingLine.cs, preserving
DateTimeKind and call counts, and update the DI registration under
Infrastructure/DependencyInjection.

testability-obstacle

dotnet-test@1.0.0

Adds the smallest production seam for one bounded behavior that needs deterministic tests — DateTime, Task.Delay, File, Environment, Guid, or Random — with no real I/O.

  • Making a Task.Delay in a receiving retry path controllable so the test does not actually sleep.
  • Deterministically testing a DAO timeout path that currently depends on wall-clock time.
  • Adding a seam that preserves the existing static API so no callers change.
Prerequisites
One bounded behavior plus a deterministic test, in a C#/.NET workspace.
Boundaries
For the single seam one behavior needs, not a broad wrapper migration.
Use the testability-obstacle skill for the retry loop in Module_Receiving
that calls Task.Delay. Add the smallest seam that lets a test override the
delay without real waiting, preserve the current public API, and point to the
test file in MTM_Receiving_Application.Tests/.

  • Verifying a test actually guards the no-ViewModel-to-DAO rule rather than just compiling.
Prerequisites
Existing tests plus the production code they claim to cover.
Boundaries
Finds gaps; closing them is a separate code-testing step.

testability-migration

dotnet-test@1.0.0

An internal specialist for the test-engineer that inventories static dependencies and migrates named seams through selection, call-site migration, wiring, and deterministic tests.

  • Running a full static-dependency inventory for a module before a broad migration.
  • Selecting the right seam for a DateTime or File dependency across many call sites.
  • Wiring production and tests together so migrated code stays deterministic.
Prerequisites
A broad .NET testability migration, usually invoked by the test-engineer.
Boundaries
For named, scoped migrations — a single bounded seam is testability-obstacle.
Use the testability-migration agent to inventory static dependencies
across Module_Settings.Core and migrate DateTime.UtcNow call sites to
TimeProvider, including DI wiring and deterministic tests in
MTM_Receiving_Application.Tests.

Using the testability family in order

  1. Find what is untested with find-untested-sources.
  2. Check whether a static dependency blocks testing with detect-static-dependencies.
  3. If it does, add a seam with generate-testability-wrappers or migrate an existing call with migrate-static-to-wrapper.
  4. Write the tests that were previously impossible.
  5. Ask test-gap-analysis whether the new tests would actually catch a regression.

Documented in testing

Test execution and coverage tools live in the testing chapter because that is where a reader looks for them: run-tests, filter-syntax, platform-detection, mtp-hot-reload, scaffold-dotnet-test-project, coverage-analysis, crap-score, code-testing-agent, code-testing-extensions, and test-analysis-extensions.

Order matters. Plan with context-map or refactor-plan before editing, then work the testability family left to right: find what is untested, remove the static obstacles, write the tests, and finally ask test-gap-analysis whether they would actually catch a regression. context-architect is the agent that does the mapping hands-off, and run-tests is the only entry here that executes the suite.
