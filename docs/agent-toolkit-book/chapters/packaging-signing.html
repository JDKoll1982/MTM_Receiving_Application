Chapter 05

Packaging, signing, and distribution

Turning the built application into something another machine can install: MSIX packages, certificates and signatures, package identity, and the manifest that ties them together.

The receiving app targets net10.0-windows10.0.22621.0 with Microsoft.WindowsAppSDK 2.4.0 and is currently unpackaged (WindowsPackageType=None), so packaging is a deliberate step here, not a default. Both Package.appxmanifest and appxmanifest.xml sit at the repo root, with MTMIcon.ico as the application icon and app.manifest alongside the project file.

winapp-package

winappcli@0.8.0

Builds an MSIX installer from an existing build output or a project file, optionally signing it as part of the pack.

  • Turning the unpackaged MTM_Receiving_Application build into an MSIX for a pilot install on warehouse PCs.
  • Choosing MSIX deliberately after WindowsPackageType=None, rather than inheriting a packaged default.
  • Re-packaging from bin output without re-running a full dotnet build.
Prerequisites
A successful build of MTM_Receiving_Application.csproj, or the project file to pack; a certificate or PFX if the package must be signed.
Boundaries
Packs what you point it at. It does not author the appxmanifest content or decide package identity.
Use winapp-package to build an MSIX for MTM_Receiving_Application.csproj.
The app is currently unpackaged (WindowsPackageType=None), so this is an explicit
packaging step, not a re-default. Pack the built output, sign it if a certificate
is configured, and write the installer under build/msix/.

winapp-signing

winappcli@0.8.0

Signs an existing MSIX or executable and manages the certificates and PFX files used for signing.

  • Signing a freshly built MSIX so it installs without the unknown-publisher SmartScreen warning.
  • Creating or importing a test PFX used only inside this repo and never committed.
  • Re-signing an executable after a patch release without rebuilding the package.
Prerequisites
An existing .msix or .exe, plus a certificate or PFX.
Boundaries
Signs and manages keys. It does not build packages or change package identity.
Use winapp-signing to sign the MSIX I just built for MTM_Receiving_Application.
Generate a test PFX if none exists, store it outside the repo so it never gets
committed, then sign the package and verify the signature.

winapp-identity

winappcli@0.8.0

Configures the package identity that Windows APIs need for push notifications, background tasks, share target, and startup task.

  • Wiring an identity to support a future background task that polls receiving queues.
  • Registering as a share target if the app starts accepting shared part numbers.
  • Setting a startup task so the receiving app auto-launches at sign-in on dock PCs.
Prerequisites
A packaged app with an appxmanifest in place.
Boundaries
Manages identity fields. It does not implement the background task or notification logic that consumes them.
Use winapp-identity to add a startup task to the package identity for
MTM_Receiving_Application, using Package.appxmanifest at the repo root, so the app
can auto-launch at sign-in on receiving dock PCs.

winapp-manifest

winappcli@0.8.0

Authors and edits appxmanifest.xml: capabilities, declarations, visual assets, and dependencies.

  • Adding a capability or declaration the app needs without hand-editing XML.
  • Pointing the manifest at MTMIcon.ico so the tile and taskbar show the right icon.
  • Keeping both Package.appxmanifest and appxmanifest.xml at the repo root in sync.
Prerequisites
A Windows app project. Both Package.appxmanifest and appxmanifest.xml exist at the repo root for this app.
Boundaries
Edits manifest content. It does not build or sign the package.
Use winapp-manifest to edit appxmanifest.xml for MTM_Receiving_Application.
Keep Package.appxmanifest at the repo root in sync, set the application icon to
MTMIcon.ico, and add any capability the MSIX needs. Do not delete either file.

winapp-setup

winappcli@0.8.0

Runs winapp init or winapp restore to add Windows SDK and Windows App SDK support, or to restore SDKs pinned in the project.

  • Restoring the pinned Microsoft.WindowsAppSDK 2.4.0 after a clean clone.
  • Initializing SDK support in a new project that does not yet reference the Windows App SDK.
  • Verifying the toolchain before a packaging run.
Prerequisites
A project or directory to operate on, and network access for restore.
Boundaries
Sets up SDKs. It does not package, sign, or edit manifests.
Use winapp-setup to run winapp restore against MTM_Receiving_Application so the
pinned Microsoft.WindowsAppSDK 2.4.0 runtime is restored before I build the MSIX.

winui-packaging

winui@0.8.0

Packages, signs, and prepares a WinUI 3 app for Store publishing, including Native AOT and self-contained deployment.

  • Packaging the WinUI 3 receiving app as MSIX with WinUI-specific template knowledge.
  • Deciding between APPX and MSIX and applying WindowsAppSDKSelfContained for a self-contained install.
  • Planning Native AOT where it fits without breaking the WinUI XAML runtime.
Prerequisites
A WinUI 3 project targeting net10.0-windows10.0.22621.0 with Microsoft.WindowsAppSDK 2.4.0.
Boundaries
WinUI-specific. Use winapp-package for a non-WinUI Windows app.
Use winui-packaging to package MTM_Receiving_Application as MSIX. It targets
net10.0-windows10.0.22621.0 with Microsoft.WindowsAppSDK 2.4.0 and currently runs
unpackaged (WindowsPackageType=None), so explain the APPX vs MSIX choice and whether
WindowsAppSDKSelfContained should stay true.

winui-setup

winui@0.8.0

Installs and verifies WinUI 3 prerequisites: .NET SDK, WinApp CLI 0.7+, and Developer Mode.

  • Confirming the toolchain before building the receiving app.
  • Enabling Developer Mode for unpackaged F5 runs.
  • Verifying the WinApp CLI meets the 0.7+ floor.
Prerequisites
A Windows 11 machine and local admin rights to enable Developer Mode.
Boundaries
Verifies prerequisites only; it does not package or sign. Note the winapp CLI 0.8.0 is already installed on this machine, and winapp --version prints nothing, so use winapp --help to confirm the version.
Use winui-setup to verify the WinUI 3 prerequisites for MTM_Receiving_Application.
Confirm the .NET SDK, Developer Mode, and the winapp CLI. winapp 0.8.0 is already
installed on this machine, and winapp --version prints nothing, so use
winapp --help to confirm the version.

Where winui and winappcli overlap

TaskPreferWhyUse the other when
Packaging a WinUI 3 app winui-packaging It knows the WinUI template, Native AOT, and the APPX vs MSIX distinctions. You are packaging a non-WinUI Windows app, so use winapp-package.
Setting up prerequisites winui-setup It owns the WinUI-specific prerequisite chain including Developer Mode. You only need SDK restore or init on a non-WinUI project, so use winapp-setup.

Choosing between them. This repo is WinUI 3, so default to winui-packaging and winui-setup for packaging and prerequisites. Fall back to winapp-package and winapp-setup only for non-WinUI Windows work. Reach for winapp-manifest and winapp-identity for the manifest and identity details the packaging skills do not author, and winapp-signing whenever a package or executable needs a signature.
