Chapter 03

Testing

Writing and running the test suite. Everything here operates on MTM_Receiving_Application.Tests/, which is xUnit with FluentAssertions, method names of the form MethodName_ShouldResult_WhenCondition, integration tests built on IAsyncLifetime, and test data prefixed TEST-.

Unit tests cover FluentValidation validators and view models that depend only on IMediator; integration tests cover view models with concrete services, handlers with concrete DAOs, and the DAOs themselves. Run the suite with dotnet test MTM_Receiving_Application.Tests/MTM_Receiving_Application.Tests.csproj; the solution file is MTM_Receiving_Application.slnx.

Corrects MSTest assertion, attribute, and lifecycle usage in supplied test code rather than authoring new cases.

Prerequisites

convert the file to xUnit.

Writes failing tests first, describing the desired behavior from issue or spec context before any implementation exists.

  • Capturing the acceptance criteria from a spec as failing xUnit tests before coding.
  • Writing the validator tests that fail until the new FluentValidation rules are added.
  • Driving a DAO method's contract into a failing test before the method exists.
Prerequisites

Boundaries

Use the tdd-red agent to write failing xUnit tests for the new

tdd-green

testing-automation@1.0.0

Implements the minimal code that satisfies failing tests and makes them pass without over-engineering.

  • Implementing a FluentValidation validator to turn the red tests green.
  • Adding the smallest DAO method body that satisfies its failing contract test.
  • Making an IMediator-only view model command pass without extra features.
Prerequisites
Failing tests from the red phase. It implements, minimally.
Boundaries
Green phase only; cleanup and design belong to tdd-refactor.
Use the tdd-green agent to implement the minimal Module_Receiving validator
that makes the red xUnit tests pass. Do not add rules beyond what the failing tests
require, then run the test project to green.

testing-automation@1.0.0

Improves code quality, security, and design while keeping the tests green.

  • Simplifying a DAO method's control flow without changing its tested behavior.

Documented elsewhere

Test analysis tools live in two other chapters so each tool has exactly one home. Audits of existing tests are in the code quality chapter: assertion-quality, grade-tests, test-anti-patterns, test-smell-detection, test-tagging, code-testing, and test-quality-auditor.

Gap analysis and testability seams are in the context, planning, and testability chapter: find-untested-sources, detect-static-dependencies, generate-testability-wrappers, migrate-static-to-wrapper, testability-obstacle, test-value-evidence, test-gap-analysis, and the code-testing-* worker agents.

Choosing between them. Author one-off tests with code-testing; run a full pipeline with test-engineer. Wrap statics with generate-testability-wrappers or migrate them with testability-migration. Drive new behavior test-first with tdd-red, tdd-green, and tdd-refactor. For the audit skills that grade and inspect existing tests, see the code quality chapter.
