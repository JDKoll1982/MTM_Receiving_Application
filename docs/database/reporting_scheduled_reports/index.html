🗄️ Table

reporting_scheduled_reports

Configuration rows for reports that are meant to run and email themselves on a recurring schedule — who receives them, how often, and when they last ran.

Overview

This table holds settings, not results. Each row pairs a report type with a human-readable schedule string, a recipient list, and an active flag. The next_run_date and last_run_date columns let the reporting module work out what is due.

Because the schedule is stored as free text, the schedule semantics live in application code — changing the wording of a schedule string in the database is not the supported way to change timing.

Indexes

Usage Notes

  • The idx_next_run and idx_active indexes are designed to be used together: WHERE is_active = 1 AND next_run_date <= NOW().
  • is_active = 0 is how a schedule is paused; do not delete the row if you only want to stop it running.
  • next_run_date being NULL with is_active = 1 means the schedule has never been calculated — it will not fire until it is.
  • created_by stores an auth_users.id, not an employee number or username.
  • Recipient addresses are stored as one comma-separated string, so reporting queries should not assume one address per row.
